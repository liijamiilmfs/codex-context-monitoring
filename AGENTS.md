# Repository Working Agreement

## Project overview

`codex-context-monitoring` is a Python application for analyzing and visualizing Codex session usage across Codex Desktop on Windows and Codex CLI.

## Technology and layout

- Python 3.14 or newer.
- `uv` manages Python, dependencies, environments, locking, and builds.
- Ruff formats and lints Python.
- ty performs static type checking.
- pytest runs the test suite, pytest-mock isolates unit-test subjects from external dependencies, and coverage.py measures unit-test coverage.
- Source uses the `src` layout under `src/codex_context_monitoring/`.
- Unit tests live under `tests/unit/`. Opt-in integration tests live under `tests/integration/`. Test modules use `test_*.py` names.
- GitHub automation lives under `.github/`.

## Setup

Install the locked development environment from the repository root:

```powershell
uv sync --locked --all-groups
```

Do not replace `uv`, introduce another environment manager, or add a production dependency without explicit approval. Commit `uv.lock` whenever an approved dependency change updates it.

## Development workflow

Inspect the working tree before editing. Preserve unrelated and uncommitted work.

Use test-driven development for behavior changes:

1. Add or update a focused test.
2. Run it and observe the expected failure.
3. Implement the smallest passing change.
4. Run the focused test and then the full quality gate.

Keep package code in `src/codex_context_monitoring/`. Keep tests outside the package in `tests/`. Add abstractions only when current behavior requires them.

## Required validation

Run the complete local quality gate before reporting an implementation complete:

```powershell
uv run ruff format --check .
uv run ruff check .
uv run ty check
uv run coverage run -m pytest tests/unit -m "not integration"
uv run coverage report
uv run coverage xml
uv build
uv lock --check
```

Run one test file or a selected test during development with:

```powershell
uv run pytest tests/unit/test_package.py
uv run pytest tests/unit -k "test_name"
```

Report every validation command and its pass or fail result. Do not claim that GitHub-hosted Ubuntu checks ran when only local Windows checks ran.

## Python style

- Target Python 3.14 and use modern Python syntax.
- Add type annotations to new functions, methods, and public data structures.
- Keep imports sorted and code Ruff-clean.
- Prefer small, explicit modules and pure functions for metric calculations.
- Keep parsing, metric computation, persistence, and visualization concerns separate as those layers are introduced.
- Do not hide malformed session data or silently invent missing values. Preserve unknown data or return a clear validation error according to the relevant contract.
- `CHANGELOG.md` is generated by Release Please and is explicitly excluded from Ruff formatting and lint checks.

## Tests

- Add tests for every behavior change and regression fix.
- Test public behavior and edge cases rather than implementation details.
- Unit tests must exercise the system under test without real external dependencies.
- Use pytest-mock's `mocker` fixture to replace network clients, subprocesses, clocks, filesystem boundaries, environment access, databases, and external services used by the system under test.
- Do not make real external calls from unit tests or introduce hand-written mock frameworks when pytest-mock can express the boundary.
- Mark every integration test with `@pytest.mark.integration` and place it under `tests/integration/`.
- Integration tests are always opt-in. Run them locally only with `uv run pytest tests/integration -m integration`.
- Never run integration tests in CI. CI may explicitly exclude the `integration` marker, but it must never select `tests/integration` or `-m integration`, use integration credentials, or start external test services.
- Preserve `tests/unit` as pytest's default `testpaths` and the default `not integration` marker exclusion.
- Preserve branch coverage and the configured 100% unit-test coverage threshold. Integration tests must not contribute to the required coverage result.
- Keep fixtures sanitized. Never commit real session data that contains user content, credentials, machine paths, repository secrets, or other sensitive values.
- Prefer small inline samples until shared fixtures provide clear reuse.

## Build and artifacts

Build with `uv build`. The command produces a wheel and source archive under `dist/`.

Build artifacts are local validation output and must remain uncommitted. This project is not published to PyPI. Do not add PyPI publishing, trusted-publisher configuration, registry credentials, or package-upload steps unless Josh explicitly changes that scope.

## GitHub automation requirements

- CI must run Ruff formatting, Ruff linting, ty, a package build, and unit-only pytest with coverage. Unit tests and the coverage gate must run on Ubuntu and Windows; integration tests must never run in CI.
- CI must upload the unit-test `coverage.xml` report to Codecov for `liijamiilmfs/codex-context-monitoring` after the coverage gate passes.
- CodeQL must analyze Python with the security-and-quality query suite.
- Dependabot must update the `uv` ecosystem and pinned GitHub Actions.
- Release Please must manage release pull requests, tags, and GitHub Releases only.
- Keep current implementation and release-status snapshots in the README `Current state` section, not in this file.

When changing GitHub Actions:

- Pin third-party actions to full commit SHAs and retain the version comment.
- Keep permissions at the least privilege required by each job.
- Set `persist-credentials: false` for checkout steps unless a documented later step requires Git credentials.
- Preserve the Ubuntu and Windows test coverage unless scope is explicitly changed.
- Validate workflow syntax and run a workflow security audit when tooling is available.

Use Conventional Commits for approved published commits because Release Please derives versions and release notes from them. Local implementation does not authorize staging, committing, pushing, opening a pull request, merging, or creating a release.

## Security and data handling

- Agents must never handle actual credentials, tokens, session secrets, or raw private prompts. This prohibition includes reading, requesting, accepting, retrieving, generating, copying, transforming, validating, storing, printing, logging, transmitting, or deleting them.
- Never ask Josh or another user to paste sensitive values into chat, a command, a file, a test fixture, or tool input. Agents may use only obvious placeholders and sanitized synthetic fixtures.
- If a task would require access to sensitive values, stop before taking that action and escalate it to Josh. State the required user-managed action without requesting or exposing the value.
- If sensitive material is encountered unexpectedly, do not inspect it further or reproduce it. Stop and report only the sanitized category, location, and count, then ask Josh to handle or remove it.
- GitHub credentials must remain user-managed in repository or organization secrets. Release Please requires `RELEASE_PLEASE_TOKEN`, and Codecov requires `CODECOV_TOKEN`; agents must never access or handle either value.
- Treat imported session-usage files as untrusted input.
- Validate file size, structure, field types, and supported schema versions before processing them when ingestion is implemented.

## Scope boundaries

- Do not perform framework upgrades, dependency swaps, broad rewrites, deployments, or destructive changes without explicit approval.
- Do not add a database, hosted service, telemetry, authentication, or external integration until the relevant requirement approves it.
- Do not commit, push, publish, merge, deploy, or move project work to a completed state unless Josh explicitly requests that action.
- Update this file when the architecture, commands, validation requirements, or release process materially changes.
